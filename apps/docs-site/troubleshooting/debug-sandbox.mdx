By default, a Sandbox is destroyed after each Attempt ends. Most problems can be located first with `niceeval show @<attempt-locator>` or `niceeval view` by looking at the verdict, assertions, file changes, commands, and conversation. For the full workflow, see the [Debugging guide](/troubleshooting/debugging).

Some problems, though, can only be seen in a live environment:

- **The environment does not start**: installing dependencies fails during setup, or the agent CLI cannot start. The agent has not started running yet, so the conversation record is empty. The fastest fix is to enter the Sandbox and rerun the install command by hand.
- **The change is outside `git diff`**: which packages were installed globally, what configuration was written under `$HOME`, and what `PATH` actually is. The saved file changes do not include these.
- **Rerunning is too slow**: a cold start plus installation takes minutes. When you want to test guesses one by one, keeping the environment is much faster than rerunning every time.

## Keep the state while running

Add `--keep-sandbox` to `niceeval exp`:

```bash
pnpm exec niceeval exp local onboarding/tool-first --keep-sandbox        # Same as --keep-sandbox=failed
pnpm exec niceeval exp local onboarding/tool-first --keep-sandbox=all    # Keep passing ones too
```

`--keep-sandbox` has two settings:

- `failed` (the default) keeps Attempts whose verdict is `failed` or `errored`, including ones interrupted by a timeout.
- `all` keeps passing ones too. Use it when tuning a setup Hook or checking the real state of the environment when it passes, so you do not have to make an eval case fail on purpose.

Without this flag, everything is destroyed. A run with `--keep-sandbox` always really executes and never reuses earlier results.

When the run ends, the summary lists which Sandboxes were kept and how to enter them:

```text
Kept sandboxes (1)
  @0123456789ABCDEFGHJKMNPQRS  onboarding/tool-first #1  errored  docker · a3f9c2d1
             enter: niceeval sandbox enter a3f9c2d1
Stop them with: niceeval sandbox stop --all
```

Each line gives three things: the Attempt locator, the Sandbox instance id, and the command to enter the environment. To see the results saved for this Attempt, use `niceeval show @<attempt-locator>` or `niceeval view --run <run-id>`.

Kept Sandboxes do not keep running and consuming resources: Docker containers stop on disk, E2B microVMs pause billing, and Vercel saves the file system.

## Enter the environment

```bash
pnpm exec niceeval sandbox enter a3f9c2d1
```

`niceeval sandbox enter` wakes the environment first, then opens a shell in the working directory. Inside is the environment as it was when this Attempt finished, so you can run commands, browse files, and reproduce the failure by hand.

After you exit the shell, the environment goes back to sleep automatically. To keep it running, add `--leave-running`.

## Inspect and clean up

The project keeps a record of kept Sandboxes. Manage them with `niceeval sandbox`:

```bash
pnpm exec niceeval sandbox list              # List kept Sandboxes and their state
pnpm exec niceeval sandbox enter a3f9c2d1    # Wake and enter; goes back to sleep on exit
pnpm exec niceeval sandbox stop a3f9c2d1     # Destroy the given Sandbox (the id can be a unique prefix)
pnpm exec niceeval sandbox stop --all        # Destroy all
```

These management commands do not read `niceeval.config.ts`. Even when the configuration file cannot run for now, you can still inspect or destroy environments. The commands read `.env` to prepare Provider credentials; when `.env` cannot be read, fix it first and retry.

The `sandbox` commands have no `--json` output. `niceeval sandbox list --json` reports `Unknown option '--json'` directly and does not go on to print human-readable text.

`stop` can be run repeatedly. A Sandbox that is already gone (deleted by hand, or expired in the cloud) is not an error; the command just removes the record and says so. If the Provider fails to destroy it, the command keeps the record and returns an error so you can retry later, and it does not hide a resource that is still alive from the list.

There is also a reminder if you forget to clean up: at the start of the next run, if Sandboxes from earlier are still kept, the terminal prints one line about it.

## Provider differences

- **Docker**: the container stops on disk, uses no memory, survives a Docker restart, and starts automatically when you enter it. Containers never disappear on their own, so Docker is the only Provider that needs active cleanup. Besides `niceeval sandbox stop`, you can also check directly with `docker ps -a -f label=niceeval.keep-candidate=true`.
- **E2B**: the microVM is paused, and files and memory are saved together. Billing stops while it is paused, it is kept indefinitely, and it resumes automatically when you enter it.
- **Vercel Sandbox**: the microVM is stopped. The file system is saved and can be resumed later, but memory state is not kept, so processes must restart after waking. After the Provider's retention period passes, `niceeval sandbox list` marks it `expired`.
- **Custom Providers**: Providers created with `defineSandbox` do not support keeping environments. The later `sandbox stop` does not load user configuration, so it cannot safely recover the destroy function you wrote in a new process.

## Boundaries

A kept Sandbox is only for investigation. It cannot continue running, and it cannot be rescored. Verdicts, assertions, and file changes follow the saved results. Nothing you change in the environment is written back to the results. For how to view results, see [View run results](/tutorials/viewing-results).

Sandboxes left behind by a forced kill are not registered and do not appear in `sandbox list`. For how to reclaim them, see [Recover after a forced kill](/troubleshooting/recover-after-kill#reclaim-sandboxes-left-by-a-forced-kill).

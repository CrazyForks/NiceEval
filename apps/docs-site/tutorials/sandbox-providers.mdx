A Coding Agent needs an environment where it can freely change files and run commands without touching your machine. That isolated environment is the Sandbox, created and destroyed by a Provider.

NiceEval provides three official Providers: local Docker, Vercel, and E2B. Docker is the most convenient for local debugging; when you need heavy parallelism, or your machine cannot keep up, switch to Vercel or E2B in the cloud.

Whichever Provider you use, evals and Adapters see the same `Sandbox` interface. Switching Providers changes one line in the Experiment, and the evals stay unchanged.

## Choose a Provider

Start by choosing based on where you run evals:

| Provider | Suits | What you need |
| --- | --- | --- |
| Docker | Local development and standard CI. Simple, controllable, no cloud dependency | Local Docker. Machine resources are limited, and cold starts and dependency installs can be slow |
| Vercel Sandbox | When you need cloud isolation, more resources, or a more stable environment | A Vercel token or OIDC configuration |
| E2B | When you need heavy parallelism, or want to use a ready-made Agent template directly | An E2B account and `e2b auth login` |

Choose one in the Experiment's `sandbox` field:

```ts
// experiments/local.ts
import { defineExperiment } from "niceeval";
import { dockerSandbox } from "niceeval/sandbox";

export default defineExperiment({
  agent: myCodingAgent,
  model: "claude-sonnet-4-6",
  sandbox: dockerSandbox({ source: { type: "image", image: "node:24-slim" } }), // or vercelSandbox({ snapshotId }) / e2bSandbox({ template })
});
```

When neither the eval nor the Experiment chooses a Sandbox, the run reports an error before creating any Sandbox; NiceEval never guesses a Provider for you.

The SDKs of the three built-in Providers are not installed with NiceEval. Install only the one you use, so unused dependencies (and their native build scripts) never enter your project:

| Provider | Install command |
|---|---|
| `dockerSandbox({ source: { type: "image", image: "node:24-slim" } })` | `pnpm add dockerode @types/dockerode` |
| `vercelSandbox({ snapshotId })` | `pnpm add @vercel/sandbox` |
| `e2bSandbox({ template })` | `pnpm add e2b` |

If it is missing, creating the Sandbox reports an error with the install command, for example `Docker sandbox requires 'dockerode'. Install it with: pnpm add dockerode @types/dockerode`. Install it as shown and run again.

### Docker Compose: `workspaceService` names the main Sandbox

When one eval needs more than one container (for example an application container plus a database), declare the whole Compose environment with `dockerComposeSandbox`:

```ts
import { dockerComposeSandbox } from "niceeval/sandbox";

sandbox: dockerComposeSandbox({
  file: new URL("docker-compose.yaml", import.meta.url),
  workspaceService: "client", // The main Sandbox
})
```

`workspaceService` names which service in the Compose file is the main Sandbox. The Agent, the commands and file operations of `t.sandbox`, `workdir`, and file change records all apply only to this one container.

Other services (databases, mock servers, and so on) are only supporting resources: you cannot `runCommand` on them, upload to them, or read and write their files, and their file changes are not visible. To use them, go over the network, for example reaching `db:5432` from the `client` container through Compose's built-in DNS.

### Let the Agent run Docker itself

When the Agent needs to run `docker build`, `docker run`, or `docker compose`, you can mount an existing Unix socket from the host, or choose raw privileged or managed rootless Docker-in-Docker. For when each mode fits, the Dockerfile, and the full configuration, see [Let the Sandbox Use Docker](/tutorials/docker-in-docker).

## Work with the Sandbox in Adapters and evals

Whichever Provider you use, Adapters and evals get the same `Sandbox` interface. Common operations:

| Method | Purpose |
|---|---|
| `runCommand(cmd, args)` | Run a command |
| `runCommandOrThrow(cmd, args)` | Run a command and throw on a non-zero exit |
| `runShell(script)` | Run a shell script |
| `runShellOrThrow(script)` | Run a shell script and throw on a non-zero exit |
| `readText(path)` / `readBytes(path)` | Read a text or binary file |
| `writeText(path, content)` / `writeBytes(path, content)` | Write a text or binary file |
| `pathExists(path)` | Check whether a path exists |
| `uploadFile(source, target)` / `uploadDirectory(source, target?)` | Upload a file or directory |
| `workdir` | The real working directory in the Provider. Omitted `cwd` / `targetDir` point here |
| `runCommand(..., { cwd })` | Run one command in another directory. Relative paths resolve against `workdir` |
| `stop()` | Destroy the environment |

The error messages thrown by the two `OrThrow` methods include the last few lines of stderr, already cleaned, redacted, and truncated. When stderr is empty, stdout is used instead. When debugging, read this summary first, and read `SandboxCommandExitError.result` when you need the full output.

## Prepare the Sandbox in order

Before the Agent starts working, the Sandbox usually needs tools installed, configuration written, and materials in place. Write these preparation steps with `.before()`, and cleanup that runs whether the run succeeds or fails with `.after()`. Every Provider function returns a `SandboxLayer` that you can keep appending steps to, and appending never modifies the original value:

```ts
import {
  changeFrequency,
  dockerSandbox,
  shell,
  writeText,
} from "niceeval/sandbox";

const sandbox = dockerSandbox({
  source: { type: "image", image: "node:24-slim" },
})
  .before(shell({
    id: "install-tools",
    command: "corepack enable && pnpm install --frozen-lockfile",
    changeFrequency: changeFrequency.rare,
  }))
  .before(writeText({
    id: "experiment-env",
    path: ".env",
    text: "FEATURE_X=1\n",
    changeFrequency: changeFrequency.frequent,
  }));
```

`changeFrequency` decides the order of steps: steps with small values that rarely change come first, and steps with large values that change often come later. That way, when only a later step changes, earlier steps can reuse the last result directly. It is an ordinary non-negative number; the built-in constants are only for readability:

```ts
changeFrequency.rare     // 10
changeFrequency.normal   // 100
changeFrequency.frequent // 1000
```

The preparation steps of the Experiment, eval group, eval, and Sandbox Agent are placed in one order: explicit `dependsOn` is satisfied first, then steps run from small to large values. So a rarely changing step in an eval group can come before a frequently changing step in the Experiment.

At run time, each preparation step appears in the progress display without leaking content:

- `shell()` shows the command you wrote, not the wrapping `/bin/sh -lc`; `command()` and `exec` show the executable and arguments.
- `writeText()` / `writeBytes()` show only the target path, byte count, and digest, not the body.
- Uploads show only the digest, target path, and byte count, not the source path on the host.
- Git checkout addresses have user info, query, and fragment removed; environment variables list only names.

Very short progress updates may be merged in the display. To reliably see fine-grained progress for a long script, split it into several smaller steps, each running long enough on its own, or report progress yourself. NiceEval does not track steps inside shell scripts. Dynamic callbacks report their own progress with `context.progress()`.

### Declare preparation cache coverage

On supported Providers, unchanged preparation steps can be reused on the next run without executing again. For this, each `.before(action)` must truthfully state which parts of the Sandbox it changes:

- Omitting `cache.state` equals `sandboxState.all`: all of this step's changes must be saveable and restorable. It is not a switch that lets the Provider pick some directories to cache.
- Write `sandboxState.dockerData` only when all of the step's changes are limited to `/var/lib/docker` in the Sandbox, which has stopped being written. For a complete Docker profile example, see [Let the Sandbox Use Docker](/tutorials/docker-in-docker#managed-rootless-dind).

`cache.state` can be written at the step definition or at a single call site, but only in one place, and a call site cannot override the definition.

The step's ID, inputs, expanded command, declared scope, and content digest are all compared automatically, and when any of them changes, the step runs again. `cache.fingerprint` only supplements version information NiceEval cannot see; it does not replace the automatic comparison.

Providers can save different scopes:

| Provider situation | Scope it can save | Result |
| --- | --- | --- |
| Local single-container Docker, with all changes in the outer container's writable filesystem | `all` | The longest unchanged run of steps from the start is reused directly |
| A Docker profile configured with a separate, pre-allocated, fixed-size storage slot and seed data | `dockerData` | Only the run of steps from the start that consecutively declare `dockerData` is reused |
| A Docker profile with shared loop or project-quota storage | None | Shows `Unsupported`; steps really execute |
| Docker Compose, E2B, Vercel, or a custom Provider | None | Shows `Unsupported`; steps really execute |

Reuse can only continue consecutively from the first step. At the first step that cannot be saved, such as a default `all` the Provider does not support, an `opaque` callback, or a scope the Provider does not support, this step and every step after it really execute. Later steps cannot be skipped even if they declare `dockerData`, because the earlier state they depend on was not saved.

On local single-container Docker, when only the final `.env` step changes, the fixed Git checkout, directory upload, and tool installation before it do not rerun. Each Attempt starts from its own independent copy of the cached result and does not inherit changes left by the previous Agent.

To confirm which steps will be reused, run `pnpm exec niceeval debug <experiment> <eval>` to see the plan; see [Check the Sandbox Plan Before Running](/tutorials/debug-lifecycle-plan).

### Define reusable preparation steps

The built-in `shell()`, `writeText()`, `uploadDirectory()`, and `gitCheckout()` are all `SandboxAction`s. When the same kind of preparation step is used in several places, you can define your own step with the same mechanism:

```ts
import { Schema } from "effect";
import {
  defineSandboxAction,
  sandboxStep,
} from "niceeval/sandbox";

const installTool = defineSandboxAction({
  id: "@acme/install-tool",
  input: Schema.Struct({ version: Schema.String }),
  cache: { fingerprint: "2" },
  steps: ({ version }) => [
    sandboxStep.exec({
      executable: "tool",
      args: ["install", version],
    }),
  ] as const,
});

const sandbox = e2bSandbox({ template: "niceeval-agents" })
  .before(installTool(
    { version: "1.4.0" },
    { changeFrequency: 20 },
  ));
```

Custom steps can only combine fixed operations NiceEval provides, and cannot access the running `Sandbox`. The rules above about cache scope and automatic comparison apply as well.

### Writing, uploading, and Git checkout

These built-in functions can be passed directly to `.before()`:

| Content source | Use |
| --- | --- |
| Existing text or bytes | `writeText()` / `writeBytes()` |
| Fixed files or directories next to the definition file | `uploadFile()` / `uploadDirectory()` |
| A fixed commit of a public Git repository | `gitCheckout()` |
| Commands as shell or argument lists | `shell()` / `command()` |

`uploadFile()` and `uploadDirectory()` take addresses such as `new URL("fixture/", import.meta.url)`, not relative paths that change with the current directory. File contents, permissions, and directory structure are compared automatically. `gitCheckout()` only accepts HTTPS addresses without credentials and full commit IDs.

Do not put hidden content that should only be provided after the Agent returns into `.before()`. First get a handle with `sandboxContent.file()` or `sandboxContent.directory()`, then call `t.sandbox.upload(handle, targetPath)` in `test(t)`. The handle carries only a content digest and does not expose host paths.

### Dynamic callbacks and cleanup

For branches that can only be decided at run time, write `.before(async (sandbox, context) => ...)` directly. The callback really executes every time, and the steps after it no longer reuse the cache.

After successfully acquiring a resource, register its release right away with `context.onCleanup()`. The closure can hold the handle obtained this time directly, so you do not need another callback that guesses the resource's state:

```ts
const sandbox = e2bSandbox({ template: "niceeval-agents" })
  .before(async (sandbox, context) => {
    const forwarder = await startLogForwarder(sandbox, {
      signal: context.signal,
    });

    context.onCleanup(async () => {
      await forwarder.stop();
    });
  });
```

`sandbox.sandboxId` in the callback is the current Sandbox's native ID on the Provider side. Normally treat it only as a value for correlation, and do not parse it. Only when this layer is explicitly bound to a particular Provider should your own trusted code hand it to the matching SDK to create helper resources for this Attempt.

These helper resources are not managed by NiceEval and are not cached; after creating them, you must immediately register a cleanup that can safely run more than once. Before the first callback starts, NiceEval may swap the underlying Sandbox instance; once a callback has started, this Attempt's cleanup and `.after()` all see the same ID.

Cleanup that must run whether the run succeeds or fails, and can safely run more than once, goes in `.after()`. All registered cleanups run in reverse registration order, and a failing earlier cleanup does not stop later ones:

```ts
const sandbox = dockerSandbox({
  source: { type: "image", image: "node:24-slim" },
})
  .before(shell({
    id: "start-helper",
    command: "./helper start",
  }))
  .after(shell.after({
    id: "stop-helper",
    command: "./helper stop || true",
  }));
```

`context.progress()` in a callback only updates the current Attempt's temporary status, and `context.diagnostic()` saves a problem to review afterwards. When the environment cannot continue, throw directly; NiceEval records this Attempt as an environment error, not as the Agent getting the task wrong.

A `defineAgent` without a Sandbox has no preparation steps. A Sandbox Agent can add command steps in the form of `sandboxLayer()` in its own `sandbox` field, but cannot choose or replace the Provider and template.

## Prebuilt environments

When the same content is downloaded or installed for every Attempt, and it is stable, expensive, or large, bake it into a prebuilt environment and let Attempts start directly from the installed environment. The three Providers are written the same way:

```ts
dockerSandbox({ source: { type: "image", image: "my-evals:node24" } })
vercelSandbox({ snapshotId: "snap_abc123" })
e2bSandbox({ template: "my-evals" })
```

For how to derive images, snapshots, and templates from official baselines, and how to carry caches between Attempts with run-time checkpoints, see [Prebuilt Sandbox Environments](/tutorials/prebuilt-sandbox).

## Retries for transient errors

When the built-in Providers create a Sandbox and hit transient failures such as rate limits, `fetch failed`, connection resets, 5xx, or temporary network unreachability, they retry automatically with exponential backoff. Configuration errors such as a missing template or missing credentials fail on the first try. When retries run out, the Attempt is recorded as `errored`. The `create` of a custom `defineSandbox` Provider is your own function, and NiceEval does not retry it for you.

`readText`, `readBytes`, `downloadFile`, `uploadFile`, file writes, and directory uploads retry a limited number of times on transient transport errors such as 429, 5xx, `fetch failed`, and connection resets. Missing files, permission errors, cancellation, and a terminated Sandbox are not retried.

`runCommand` and `runShell` do not retry automatically, because a command may already have had side effects. Retry yourself in a hook or eval only when you have confirmed a command is safe to repeat.

## Custom Providers

To connect another service, use `defineSandbox`. You are responsible for isolating the filesystem, processes, network, and credentials yourself; NiceEval does not add these security boundaries automatically to an arbitrary `Sandbox` implementation.

The `feedback` that `create` receives reports status during creation, such as allocating an instance, pulling an image, or restoring a snapshot:

```ts
import { defineSandbox } from "niceeval/sandbox";

export default defineSandbox({
  name: "modal",
  recommendedConcurrency: 8,
  async create({ timeout, runtime, feedback }) {
    feedback.progress({ message: "Allocating Modal Sandbox" });
    const instance = await allocateModal({ timeout, runtime });

    if (instance.usedFallbackRegion) {
      feedback.diagnostic({
        code: "modal-fallback-region",
        level: "warning",
        message: `Primary region unavailable, using ${instance.region}`,
        data: { region: instance.region },
      });
    }

    return new ModalSandbox(instance);
  },
});
```

The return value only needs to implement the `Sandbox` interface. `recommendedConcurrency` is the default concurrency when nothing else is set.

Do not write a Provider SDK's raw logs directly to the host process's `stdout` / `stderr`: use `feedback.progress` for temporary status, `feedback.diagnostic` for problems that should be kept, and throw when the environment cannot be created. That way the terminal's progress panel is not scrambled by logs, and CI has only one ordered output.

## Permissions and execution identity

Providers differ in their limits on the executing user, network, filesystem, and process lifecycle. When writing a Fixture, avoid depending on the host environment as much as possible, and put dependencies in `package.json` or the Fixture's preparation steps.

## Performance tips

- Bake stable heavy dependencies into an image, template, or snapshot, or write them as low-frequency `.before()` steps.
- Reduce the size of the Fixture's dependencies.
- Use small, explicit caches or pre-checks for dynamic content.
- Control `maxConcurrency` (the Experiment field or `--max-concurrency`) to avoid exhausting local Docker resources.
- Split slow checks: keep the ones that must pass as gates, and use `.optional()` for the nice-to-haves.

### Reuse Provider startup across Attempts

When Sandbox startup time dominates, declare `sandboxReuse: true` in the Experiment. Several Attempts share one Sandbox in turn: each Sandbox is created only once, each Attempt still runs its own `.before()` / `.after()`, and the working directory is reset between evals. On Docker, unchanged preparation steps can also be reused directly.

```ts
export default defineExperiment({
  agent: codexAgent(),
  sandbox: e2bSandbox({ template: "acme-evals", lifetimeMs: 60 * 60_000 }),
  sandboxReuse: true,
  maxConcurrency: 3,
});
```

Reuse is written in the Experiment file, not a command-line switch: the same experiment cannot turn it on or off temporarily. When you need fresh Sandboxes for a comparison, write a separate experiment that does not declare reuse. For the costs, how many times each lifecycle layer runs, and the requirements preparation code must meet, see [Reuse Sandboxes](/tutorials/sandbox-reuse).

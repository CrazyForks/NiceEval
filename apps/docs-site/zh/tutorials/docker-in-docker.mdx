---
title: "让 Agent 在 Sandbox 中运行 Docker"
sidebarTitle: "在 Sandbox 中运行 Docker"
description: "用 Incus VM 为每个 Attempt 提供独立内核、Docker daemon 和数据盘，并检查环境与缓存容量。"
---

Agent 需要运行 `docker build`、`docker run` 或 `docker compose` 时，使用 `incusSandbox()`。每个 Attempt 都有独立 VM，Docker daemon 运行在 VM 内，Docker 数据放在单独的数据盘上。Attempt 结束后，NiceEval 销毁这台 VM。

评估用例声明需要什么能力，Experiment 选择满足要求的环境。宿主 Docker socket、privileged 容器和 rootless DinD 不能满足这里要求的独立内核隔离。

## 准备宿主环境

先请管理员部署 Incus、可信基础镜像与 `/etc/niceeval/incus-provider.json`。描述文件使用 `niceeval.incus-provider/v2`，记录运行环境、镜像和容量。日常运行 NiceEval 的用户需要能够读取描述文件并调用 Incus CLI。

NiceEval 不负责在宿主上安装服务、挂载存储或导入基础镜像。基础镜像必须已存在，并包含 Docker CLI、Compose 与 Docker daemon。管理员应提供完整的镜像 digest、project 和 storage pool 名称。

进入评估项目，检查正式环境：

```bash
pnpm exec niceeval sandbox provider doctor incus
```

`doctor` 只读检查环境、可信镜像、对象对应关系和容量，不创建评估 VM，也不执行清理。所有项目通过后，再运行实验。

如果管理员提供的是开发环境，使用：

```bash
pnpm exec niceeval sandbox provider doctor incus --development
```

开发环境通过不代表正式环境通过。开发结果不具有正式环境的容量保证，不能与正式环境结果直接比较。

## 在评估用例里声明 Docker 能力

把能力要求放进评估用例的 `sandbox` 字段。下面要求 Compose v2、独立内核和至少 4 GiB Docker 数据空间：

```ts
import { defineEval } from "niceeval";
import { sandboxRequirements } from "niceeval/sandbox";

export default defineEval({
  sandbox: sandboxRequirements({
    docker: {
      api: "docker/v1",
      compose: "v2",
      isolation: "dedicated-kernel/v1",
      minimumDataBytes: 4 * 1024 ** 3,
    },
  }),
  async test(t) {
    await t.send("请用 Docker Compose 启动项目并验证服务可用。");
  },
});
```

不需要 Compose 时，将 `compose` 写为 `"not-required"`。评估用例不选择镜像、project 或 storage pool。

## 在 Experiment 里选择 Incus

用管理员提供的真实 digest 替换下面的示例值：

```ts
import { incusSandbox } from "niceeval/sandbox";

const sandbox = incusSandbox({
  image: "niceeval/docker-execution-v1@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  project: "niceeval-eval",
  storagePool: "niceeval-evals",
  resources: {
    cpus: 4,
    memoryBytes: 6 * 1024 ** 3,
    dockerDataBytes: 4 * 1024 ** 3,
  },
});
```

把 `sandbox` 传给 `defineExperiment()`。VM 内的工作目录是 `/home/sandbox/workspace`，命令以 `node` 用户执行。Agent 使用 VM 内的 Docker socket，不能访问宿主 Docker daemon。

开发环境需要明确选择对应的 project、pool 和许可：

```ts
const sandbox = incusSandbox({
  image: "niceeval/docker-execution-v1@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  project: "niceeval-eval-dev",
  storagePool: "niceeval-sandbox-dev",
  acceptDevelopmentDomain: true,
});
```

省略 `acceptDevelopmentDomain` 时，只接受正式环境。把它设为 `true` 后，也不能配正式环境的 project 和 pool。

运行前查看计划：

```bash
pnpm exec niceeval exp my-experiment --dry
```

计划会显示能力要求、Provider 提供的能力和所选环境。要求不满足时，NiceEval 在创建 VM 前报错，不会自动换成其它 Provider。

## 复用准备结果

把稳定的安装、文件上传和 Docker 镜像准备写成声明式 `.before()` 步骤，使用默认的 `sandboxState.all`。Incus 会保存并核对完整的准备结果，包括 VM 根盘和 Docker 数据盘；每个 Attempt 从独立副本启动。

执行顺序不变时，只调整步骤的声明位置不会使相同执行内容失去缓存。改了命令、输入或文件内容时，从发生变化的步骤开始重新准备。动态回调每次执行，它后面的步骤也真实执行。步骤写法见[按顺序准备 Sandbox](/zh/tutorials/sandbox-providers#按顺序准备-sandbox)。

缓存准备结果不等于复用运行中的 VM。Incus 不支持 `sandboxReuse: true` 或 `--keep-sandbox`，这两种配置会在创建资源前报错。

## 查看与回收准备缓存

准备缓存会占用磁盘。`doctor` 同时检查数量余量与字节余量；数量没满不代表磁盘够用。先查看对象和空间：

```bash
pnpm exec niceeval sandbox provider inventory incus --json
```

开发环境的所有维护命令都要加 `--development`。命令不加载项目配置、评估用例或 Experiment。

回收分为预览和执行两步。下面先选择七天未使用的准备缓存：

```bash
pnpm exec niceeval sandbox provider gc incus --unused-for 7d --json
```

检查预览中的候选和预计回收字节，再使用返回的 plan ID：

```bash
pnpm exec niceeval sandbox provider gc incus --apply <plan-id> --json
```

plan 有效期为 15 分钟。执行时会重新检查资源是否仍符合条件；被使用或对象信息变化的候选不会删除。有效缓存被回收后，下次运行会重新准备。

不写 `--unused-for` 时，只预览符合条件的失效或被替代记录，以及可继续处理的中断回收。NiceEval 不会自行按年龄删除有效缓存。没有登记的对象或对象信息不匹配的记录只会展示，需先查明归属。

不要直接删除 NiceEval 管理的 Incus 实例。若已有记录对应的实例和数据卷都被手动删除，用 `inventory` 检查，再通过 `gc` 预览和执行收回记录。回收中断时生成新预览；新计划会重新检查资源并继续符合条件的回收。

## 排查失败

| 看到的结果 | 下一步 |
| --- | --- |
| 找不到 Provider 描述文件或可信镜像 | 请管理员检查部署、文件权限和完整镜像 digest |
| `sandbox-capability-unsatisfied` | 检查评估要求、Experiment 的 Provider 与开发环境许可 |
| `artifact-capacity` 失败 | 查看准备缓存数量和正在使用的记录，预览可回收项 |
| `artifact-storage` 失败或 `unknown` | 检查 pool 实际可用空间和读取权限；不要仅提高数量上限 |
| `dangling` | 对象已缺失；用 `gc` 预览并收回对应记录 |
| `orphan` 或 `metadata-drift` | 查明对象归属与配置差异；GC 不会删除这些对象 |

NixOS 用户还应核对[宿主部署边界](/zh/tutorials/nixos-managed-dind)。已有 OpenSandbox 服务的连接方式见[选择并配置 Sandbox Provider](/zh/tutorials/sandbox-providers#连接-opensandbox)；服务端使用 Docker 不代表它满足本页的 Docker 能力要求。
